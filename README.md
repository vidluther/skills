# Skills

This is my collection of skills, rules, and conventions for AI coding agents (Claude Code, OpenCode, Codex), so they understand how I work and what I expect.

_Formerly "Sabu", after the sidekick from Chacha Chaudhary: Chacha is the brain, Sabu is the loyal, super-strong agent who does the heavy lifting once Chacha decides what to do. That's still the model: I'm the thinker, the agent executes._

## What's in here

- **`skills/`** — a collection of skills (capability-shaped prompts) the agent can pick up and run. Each one is a SKILL.md plus optional supporting files. The skills live by themselves so they can be invoked individually (`/marshal`, `/diagnose`, etc.) and read each other for cross-reference. Some skills can also be invoked implicitly via a discussion. For example, I can say "create issues based on the discussion we just had" and the right skill will be invoked.

The skills currently cover, roughly:

- **Project setup** — `marshal`: my way of doing an `/init` on a codebase that's new to me. Ideally run once, so the agent and I both understand the codebase and, more specifically, our intent.
- **Intent / understanding** — `rubber-duck`: I probably use this the most. I tell the agent what I want to accomplish, and then it interviews me about it, against the project's domain language and capturing decisions when the project documents them. This used to write plans, which would then be converted to issues, but lately I'm modifying this to use "intents" and to achieve an ISA (Ideal State Artifact). I may run this multiple times with different models.
- **Second / third pair of eyes** — `reconcile-plans` (the follow-up to `rubber-duck`: reconcile multiple plans or ISAs for the same work — produced by different models or sessions — into one, surfacing where they agree, where they diverge, and the catches only one model noticed, optionally convening a lens-based review council).
- **Issue workflow** — `to-issues` (break a plan or ISA into tickets; ISA-sourced tickets cite the criteria they satisfy).
- **Code review** — `review-pr`: review PRs that I have been asked to review, or were assigned to me. This will query the Jira/Github issue to understand the problem, and then look at the PR itself. Currently this gives me the cliffnotes of the changes so I can either manually add my comments, or I decide if I want the agent to write the comments. I'm not 100% comfortable with the agent understanding all the business logic, or my ability to explain the intent, but this helps me out tremendously. This is probably my second most used skill.
- **Understanding code** — `zoom-out` (map an unfamiliar area: purpose, modules, callers, where to start reading).
- **Debugging / troubleshooting** — `diagnose` (disciplined debugging loop).
- **Did we hit the goal?** — `isa-check`: runs each ISC's eval against the current code and updates the ISA's Status. This is the "are we done" check.
- **Ready to ship** — `improve-codebase-architecture`: once the goal is met, I run this to make sure we're being pragmatic about the code and to spot refactoring opportunities.
- **Version control** — `gitbutler` (GitButler operations via `but`; generated by the GitButler CLI wizard, version-stamped).
- **Skill discovery** — `find-skills` (find and install agent skills).
- **Stack-specific helpers** — `migrate-oxlint`.
- **Work context (Atlassian)** — `twg*` skills (Jira, Confluence, Bitbucket, status rollups, ownership routing), installed by the `twg` CLI via `setup.sh`; not committed here.
- **Reminders** — `remctl` (Apple Reminders, local to my Mac and hopefully more secure). I'm also testing Remember The Milk, which is a connector rather than a skill here — handy because it works in the cloud. Still figuring out which suits me.

Wondering what ISA, ISC, AFK, or a tracer bullet is? See [CONVENTIONS.md](./CONVENTIONS.md) — glossary plus example workflows.

## Getting started

```sh
git clone git@github.com:vidluther/skills.git ~/work/personal/skills
cd ~/work/personal/skills
./setup.sh
```

`setup.sh` wires the skills into every agent: one parent symlink at `~/.agents/skills` (the universal AGENTS.md-convention location), plus one symlink per skill into `~/.claude/skills`, `~/.config/opencode/skills`, and `~/.codex/skills` — so the skills become invokable via `/<name>` in any session. It also mirrors the GitButler steering block into the Codex and OpenCode instruction files. Idempotent — safe to re-run after adding skills.

## Provenance

Most of the skills are forks or evolutions of public sets — Matt Pocock's skill collection and others — adapted to my workflow. Some are bespoke. The `marshal` skill (and its state/provenance label model) was rewritten from scratch in May 2026 as part of a redesign aimed at making the harness work for any new or existing repo.

Vendored third-party skills record where they came from in their `SKILL.md` frontmatter: `source:` (upstream repo), `source_path:`, `upstream_ref:` (the commit last reconciled against), and `last_reviewed:`. The presence of `source:` is what marks a skill as third-party — `rg '^source:' skills/*/SKILL.md` lists them (currently three, all tracing back to mattpocock/skills). These are forks, not mirrors: I adapt them, so upstream is somewhere I shop for improvements on need, not a feed I sync from. To review what changed upstream before pulling anything in, run `./update-thirdparty-skills.sh <name>` — it's read-only (shows the upstream diff and a Skillspector scan; never edits `skills/`).

## Security 

I highly recommend you view the skills here, and elsewhere, before you decide to start using them yourself. Take a look at [Skillspector](https://github.com/nvidia/skillspector) and see if the skills you have do anything dangerous, and decide if you want to risk it or not.

This matters more than it looks. A skill is not documentation — it's instructions an agent *executes* while holding real tools (shell, file edits, MCP). A third-party skill is therefore code you run. That's why vendored skills here are **never auto-updated**: auto-pulling upstream would be an unattended supply-chain channel (upstream changes the prompt, your next agent run obeys it). Updates are deliberate and reviewed — `./update-thirdparty-skills.sh <name>` shows the upstream diff and runs `skillspector scan --no-llm`, you read it for injection-style changes a scanner can't catch, then you hand-merge. Don't automate that gate away.
